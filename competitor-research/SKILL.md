# competitor-research — 通用竞品调研

把一个竞品,做成一份**提炼过关键洞察**的调研结论。核心不是"它有哪些功能",而是回答三问:

1. **它的核心做法 / 设计是什么**(抓关键,不面面俱到);
2. **哪些值得借鉴**——比我方或通用方案**更好**的地方(先摸清我方现状,**剔除我方已有**);
3. **哪些是风险 / 短板**——尤其易被忽视的机制性问题。

> **重提炼、轻罗列**:不堆基础功能描述,不照搬竞品文案。每写一段先问"这对决策有用吗";没有洞察含量的内容不写。

## 触发条件

任一满足即启用:用户要求"调研 / 分析某竞品""竞品哪里更好 / 值得借鉴""梳理竞品关键流程""把竞品调研同步到飞书 / 配图 / 画流程图"。

## 四阶段主工作流

```
阶段 1  侦察定位    主体/定位/底座是否外包 → 实测公开页抓结构化内容 → 宣称溯源
阶段 2  拆解判断    核心做法 + 优缺点(多方视角) → 为该品类自建"关键机制专查清单"
阶段 3  深挖(按需)  关键流程 / 规则 / 协议 → 必要时登录态实测(用户配合)→ 守诚信红线
阶段 4  提炼输出    先提炼(值得借鉴[剔除已有] + 风险),再成文 → 可选飞书图文混排
```

### 阶段 1 · 侦察定位

- **定位主体**:从「关于我们 / 备案 / 页脚」确认运营主体、赛道、**核心能力是否外包**(常见:技术/版权挂第三方)。
- **实测抓取**:Playwright 逐页 `browser_navigate` + `browser_evaluate` 批量取导航、核心模块、定价、标签等结构化数据(SPA 留渲染等待)。抓法见 [`references/probe-playbook.md`](references/probe-playbook.md)。
- **宣称必溯源**:营销数字("覆盖 N 国""效率提升百倍")定位到**具体出处页**,标注"营销话术、数据待核实";切勿当既成事实。

### 阶段 2 · 拆解与判断

- **核心做法 + 优缺点**:每个核心功能只讲清"设计要点 + 它强/弱在哪",基础描述从简;配 **⚖️ 优缺点**(买方 / 供给方 / 平台等多方视角,✅⚠️ 各 1–2 条结论,不复述功能)。
- **为该品类自建"关键机制专查清单"**:不同品类的胜负手不同,**先想清这个品类最该盯的 3–5 个机制维度**,逐条实测。别用固定模板套。举例:
  - *交易/授权类*:定价/结算颗粒度、授权时点、身份是否绑账号、凭证存证形式、**是否需被授权人本人同意**;
  - *内容/社区类*:冷启动供给、推荐/分发机制、创作者激励与留存;
  - *SaaS/工具类*:上手门槛、集成/API 开放度、计费模型、迁移成本。
  > 每条结论都标注**归属章节**;把"单向/无需本人同意""能力外包""隐性锁定"这类**风险点**显式标 ⚠️。

### 阶段 3 · 深挖(按需 + 登录态)

- **关键流程 / 规则 / 协议**:从帮助中心 / FAQ / 条款页还原;弹窗类条款用 Playwright **点击触发 + 取 `textContent`**(弹窗常虚拟滚动)。梳理"谁、何时、什么形式、核心条款",别想当然画流程。
- **登录态实测(需用户配合)**:公开抓不到的核心界面 / 账户结构 / 样张,**请用户协助登录**(手机号 + 验证码,见 [`references/probe-playbook.md`](references/probe-playbook.md))。
- **诚信红线(不可越界)**:
  - **绝不**提交真实身份证件 / 企业证照、代填真实敏感资料;
  - **绝不**发起真实付费交易去换样张;
  - 取不到的,用 🔒 标注"需 XX 前置或真实交易方可取样,故未强行获取",边界写进文档;
  - 用户主动提供的截图 / 文本,据实纳入并注明来源日期。

### 阶段 4 · 提炼与输出

- **先提炼再成文**:动笔前先落定两张清单——**「值得借鉴」(已剔除我方已有)** 与 **「风险 / 短板」**;这两张是文档价值所在,功能描述只是支撑。
- **写「值得借鉴」前的硬性前置(最易翻车,必做)**:**先读我方产品文档 / PRD、逐条核对我方现状**,把**我方已有 / 已领先**的维度划掉,再写。否则极易把"对方已有、我方其实也有(甚至更优)"的能力误当借鉴项。宁可把对标写成"元相已有 / 领先 vs 竞品少数可借鉴",也不要凭空推荐我方早已具备的东西。
- **飞书图文混排(可选)**:用户要同步飞书时,按 [`references/lark-sync.md`](references/lark-sync.md) 写入——首次整篇 `overwrite`,增量改含图/画板的文档一律 `str_replace` / `block_*`(**禁 overwrite**);截图用 `media-insert --selection-with-ellipsis`;流程图用 `<whiteboard type="mermaid">` 画板。

## 输出骨架(按需裁剪,不必凑齐)

```
概览(主体 / 定位 / 底座是否外包 / 宣称[已溯源])
核心功能与优缺点(每功能:设计要点 + ⚖️ 优缺点)
商业模式 / 生态(如相关)
关键流程(如相关,配 mermaid 流程图)
★ 值得借鉴的点(剔除我方已有,聚焦设计手法)
★ 风险 / 短板 / 待核实(🔒 边界)
信息来源(实测日期 + 页面清单)
```
> 带 ★ 的两节是提炼产物、文档核心;其余是支撑材料,篇幅要克制。

## 边界

- **重提炼**:没洞察含量的内容不写;不照搬竞品文案、不堆功能清单。
- **只写实测**:无法验证进"待核实",宣称必溯源。
- **不臆造登录态**:取不到就 🔒 标注。
- **不越界**:不提交真实身份/证照、不发起真实交易;登录用完主动提示可退出。
- 命令配方见 [`references/lark-sync.md`](references/lark-sync.md);实测技巧见 [`references/probe-playbook.md`](references/probe-playbook.md);踩过的坑见 [`references/pitfalls.md`](references/pitfalls.md)。
